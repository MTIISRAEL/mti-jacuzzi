# מעקב ג'קוזי MTI: אשדוד ⇄ ברקן

אפליקציה וובית למעקב אחרי הזמנות ג'קוזי ביתי, מבקשת האספקה ועד הלקוח, עם שרטוט גרפי של כל ג'קוזי.
כניסה עם חשבון Google והרשאות לפי כתובת מייל.

אתר סטטי: אין בנייה ואין שרת. הקבצים מתארחים כמו שהם (GitHub Pages), והכניסה והנתונים ב-Firebase, בפרויקט `mti-orders`.

## קבצים

| קובץ | תפקיד |
|---|---|
| `index.html` | המסך הראשי וטעינת Firebase |
| `firebase-config.js` | פרטי החיבור לפרויקט `mti-orders` |
| `app.js` | כניסה, תפקידים, לוח ההזמנות, משתמשים |
| `sketch.js` | מסך השרטוט (קירות, ג'טים, ברז, מנוע, פתח שירות) |
| `models.js` | 68 דגמי האמבטיות והמידות שלהם, מתוך הקטלוג הדיגיטלי |
| `app.css` | עיצוב, כולל מצב כהה |
| `img/` | תמונות על של 34 דגמים, חתוכות לגבולות האמבטיה. ל-6 דגמים א-סימטריים יש גרסת ימין ושמאל (`-R`, `-L`). מקור: הקטלוג הדיגיטלי (catalog.mtibath.co.il) |
| `firestore.rules` | כללי ההרשאות. נשמר מקומית בלבד ולא עולה למאגר; מתפרסם מ-Firebase Console (Firestore → Rules) |

## מה מוגדר ב-Firebase (פרויקט `mti-orders`)

- Authentication: כניסה עם Google מופעלת.
- Firestore: בסיס נתונים באזור `me-west1` (תל אביב), במצב Production, עם הכללים שב-`firestore.rules`.
- כדי שהכניסה תעבוד מכתובת האתר, צריך להוסיף את הדומיין שלו ב-Authentication → Settings → Authorized domains.

## משתמשים ותפקידים

חשבון הבעלים מוגדר ב-`firestore.rules` (הפונקציה `ownerEmail()`). בכניסה הראשונה שלו נוצרת לו רשומת מנהל.
כל השאר מתווספים מתוך האפליקציה: **משתמשים → כתובת Gmail, שם, תפקיד**. מי שלא ברשימה רואה "אין עדיין הרשאה".

| תפקיד | מה מותר |
|---|---|
| מנהל | הכול, כולל משתמשים ומחיקת הזמנות |
| משרד | פתיחת הזמנה, שרטוט, אישור לקוח, חזרה שלב |
| מחסן אשדוד | קיט, קבלה מברקן, בדיקה, אריזה |
| מנהל ברקן | קבלה בברקן, התחלת איבזור, סיום איבזור |
| נהג | קבלה בברקן / באשדוד, אספקה ללקוח |
| סוכן | צפייה בלבד, רק בהזמנות שמשויכות אליו |

כל מי שאינו סוכן יכול לדווח על עיכוב.

## אישור לקוח בקישור

אחרי ששומרים שרטוט תקין, בכרטיס ההזמנה מופיעה תיבת "שליחת השרטוט ללקוח לאישור" עם כפתורי WhatsApp, SMS, אימייל והעתקת קישור.
הכפתורים פותחים את האפליקציה המתאימה במכשיר של השולח עם הודעה מוכנה; השליחה עצמה נעשית משם.
הלקוח פותח את הקישור בלי כניסה, רואה את השרטוט, ומאשר או כותב מה לשנות. אישור מקדם את ההזמנה אוטומטית להכנת קיט.
עותק השרטוט של הלקוח נשמר ב-`approvals/<token>`; מי שמחזיק בקישור יכול לקרוא רק את המסמך הזה ולענות עליו פעם אחת.

## השלבים וזמני התקן

זמני התקן (בימי עבודה, א'–ה') קובעים מתי הזמנה מסומנת כחורגת ומה תאריך האספקה הצפוי.
הם הערכה ראשונית ומוגדרים בראש `app.js` במערך `STAGES` (השדה `t`):

## מה חשוב לדעת

- **מי רשאי ללחוץ על איזה שלב** נאכף במסך בלבד. בבסיס הנתונים ההרשאה גסה יותר: סוכן לא כותב בכלל, מחסן/ברקן/נהג/משרד רשאים לעדכן הזמנות, ורק מנהל מוחק.
- **תבנית ג'טים סטנדרטית** קיימת רק ל-MTI-114 (BASIC ו-TITANIUM). בשאר הדגמים מסמנים ג'טים ידנית.
- **תמונת על** יש ל-34 מתוך 68 הדגמים. בשאר (בעיקר פינתיות סימטריות ומלבניות שהתמונה שלהן בקטלוג לא בקנה מידה) השרטוט נפתח על מתאר סכמטי במידות הדגם.
- **דגמים עם כיוון** (MTI-26, 28, 29, 52, 53, 59): חובה לבחור ימין או שמאל בשרטוט; החלפת כיוון הופכת את כל השרטוט.
- **מספר סידורי** בן 4 ספרות נקבע באשדוד בפתיחת ההזמנה. תבניות נוספות מוסיפים ב-`TEMPLATES` בראש `sketch.js`.
- **בשרטוט מסמנים** קירות, ג'טים (2" או 3"), ברז, מזלף ופתח שירות. מנוע ויניקה לא מסומנים בשרטוט; סוג המנוע נבחר מרשימה (WPPE120, JA120, JA150, JA200, ו-WP-300-I / WP-300-II כשיש מערכת הפעלה) ונכנס לקיט. מיקום פתח השירות ההתחלתי הוא ניחוש ולא נלקח משרטוט ייצור.
- אי אפשר לסמן "הלקוח אישר" בלי שרטוט שמור ותקין. אחרי האישור השרטוט ננעל.
